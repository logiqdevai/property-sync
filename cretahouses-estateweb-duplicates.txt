CRETAHOUSES.GR -- DUPLICATE ESTATEWEB PROPERTY LISTINGS
Generated: 2026-08-13

ROOT CAUSE
----------
cretahouses.gr shows its internal listing id as "#NNNN" (leading hash) on each property
page. The scraper stored that raw value verbatim into property_id/internal_id (fixed
earlier today in api/src/integrations/crawler/utils/crawler.utils.ts).

Every CMS sync run for a cretahouses property first tries to find its existing EstateWeb
listing via EstateWebPropertyReconciliationService.reconcileCreate(), which looks up
normalizeCode(userProperty.internal_id) against the live EstateWeb code catalog
(api/src/integrations/estateweb/services/estateweb-property-reconciliation.service.ts,
lines 80-88). Because internal_id was "#1987" etc., it could never match a real EstateWeb
code (EstateWeb codes are plain numbers), so reconciliation always returned "not matched",
and api/src/background/cms-sync.processor.ts (CREATE branch, line ~411) fell through to
creating a BRAND NEW EstateWeb property instead of reusing/updating the existing one.

Only the most recently created id is ever stored on user_properties.integration_property_id,
so every earlier push became an orphaned duplicate that stayed live in EstateWeb, unlinked
from anything in our database. This has been happening on every crawl/sync cycle for
cretahouses listings for a long time -- the oldest orphan found dates to 2023-07-04, with
further waves on 2026-08-11, 2026-08-12, and 2026-08-13.

This is a PRE-EXISTING bug, not something introduced by the code-alignment migration done
earlier today. That migration only PATCHed the code field on the currently-linked id already
stored in user_properties.integration_property_id -- it never created a new EstateWeb
property. The "#" fix already deployed in this repo also fixes reconciliation going forward,
so this should stop recurring on future syncs, but the already-created orphans below need
manual cleanup directly in EstateWeb (this app has no delete-property capability wired up).

Matching method: grouped live EstateWeb listings by (normalized description text + price)
so that reused marketing boilerplate across different real properties could not cause a
false match. Every one of the 159 currently-linked cretahouses properties landed in exactly
one group with exactly one KEEP -- no group had zero or multiple correctly-linked entries.

Partially, not fully — and I want to be precise about where the fix does and doesn't reach.

**What's fixed:** The core mechanism that caused this — `EstateWebPropertyReconciliationService.reconcileCreate()` looking up `normalizeCode(internal_id)` against the live EstateWeb code catalog and always failing to match because `internal_id` had a `#` prefix — is fixed at the source (`extractSourcePropertyIds` now strips it on every future crawl). For the **153 properties** whose `internal_id`/`property_id` and EstateWeb `code` are now aligned, the next sync should correctly find the existing listing by code and UPDATE it instead of creating a new one. That should stop new duplicates for those.

**What's NOT fully covered:**

1. **The 6 collision properties** — the ones I skipped because their target code was already owned by a different EstateWeb listing — are still misaligned. Their `internal_id` still won't match any live `code`, so reconciliation will keep failing for those specifically, meaning they're still exposed to creating fresh duplicates on the next sync unless resolved manually.

2. **A second, separate bug** — the Aug 11 crawl run created 281 EstateWeb records from only 176 local properties found, i.e., more creates than properties in a single run. That's not the code-mismatch issue; that's a duplicate-enqueue race condition (already flagged in this repo's own `docs/INCIDENT-ESTATEWEB-DUPLICATE-PROPERTIES.md`). Nothing done in this session touched that — if it's a genuine race in how CMS-sync jobs get queued/processed, it could still create duplicates even for properties whose codes are now perfectly aligned.

3. **The 288 existing orphans don't self-heal.** Fixing reconciliation going forward doesn't retroactively merge or clean up what's already sitting live in EstateWeb — those still need manual handling.

So: the specific failure mode you hit is closed for the 153 aligned properties, but I wouldn't call it "guaranteed no more duplication" until the 6 collisions are resolved and that queue-race bug is actually investigated.
