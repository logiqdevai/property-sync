## #1 — Root cause & fix (confirmed against production data)

**Root cause:** `syncForProperty` truncates each property's canonical images to the tracker's `max_image_count` (`mapFromCanonical` → `truncateImages`), then compares the *whole* truncated array against what was previously stored to decide whether to re-run the paid Dewatermark pipeline (`imagesChanged`). Raising `max_image_count` (e.g. 1 → 8) on an already-tracked agency makes that array longer for **every existing property** on the very next sync — not because the source photo changed, but because the truncation window widened and now exposes canonical images at positions 2–8 that were always there but never kept before. The array-length difference alone made `imagesChanged` true, which silently re-ran `applyTrackerWatermarkPipeline` (a real paid call to the Dewatermark API) against the agency's entire back catalog on its next scheduled crawl — not just new listings.

**Confirmed in the production DB (read-only queries against `cost_logs`):**
- 4 tracked agencies (`bitsimis-real-homes`, `asiminarealestate`, `cretahouses`, `nikiestate`) were all changed to `watermark_image_count: 8` / `max_image_count: 8` on 2026-09-30 ~18:29–18:30 UTC (21:29 Athens) — matching the client's description exactly.
- Baseline Dewatermark usage for this account is 1–7 calls/hour. Between 03:00–04:00 UTC on 2026-10-01 (the agencies' next scheduled crawl) there was a spike of **320 calls in one hour** — 310 against `asiminarealestate`, 10 against `cretahouses` — matching the client's "~300 credits" report almost exactly.
- Every one of the 41 billed properties in that burst was created well before the burst (oldest: 2026-08-11, newest: 2026-09-12) — confirming these were pre-existing properties being silently reprocessed, not new listings.

**Fix applied** (`api/src/modules/user-properties/user-properties.service.ts`): added `imagesOverlapChanged`, which only compares the index range both the old and new image arrays share. A genuine content swap inside that shared window still triggers the watermark pipeline as before; a cap increase that merely exposes new trailing positions no longer does. The extra images still get saved and shown on the property (per `max_image_count`/the "show first 8 photos" intent) — they're just not auto-sent to the paid Dewatermark API for the back catalog anymore. `tsc --noEmit` passes.

**Not yet done / for discussion:** there's currently no way to *intentionally* backfill-dewatermark the newly-exposed images on existing properties — e.g. if the client genuinely wants photos 2–8 of already-tracked listings dewatermarked too, that now requires a deliberate action (not yet built) rather than happening automatically. Worth a short follow-up conversation with the client on whether that's wanted, and if so, as an explicit opt-in action (so the credit cost is visible before it's spent) rather than an automatic side effect of changing a setting.

## #4 — Real root-cause fix: why our stored code didn't match the source agency's code at all

Client pushback, correctly: the above was a matching-layer workaround, not a real fix — if a source agency's code is `"4-2569"`, property-sync should store `"4-2569"`, not `"2569"`, so nothing needs special-case matching in the first place.

**Found it:** `bitsimis-real-homes.gr`'s detail page renders its code *only* inside a labeled specs table (`_detail_specs: {"Κωδικός": "4-2569", ...}`), never inside the free-text description. property-sync's generic code extraction (`extractSourcePropertyIds` in `api/src/integrations/crawler/utils/crawler.utils.ts`) only ever searched the free-text description/title for a `"Κωδικός: ..."` pattern — it never looked at the structured specs table at all. So for this listing the free-text search found nothing, and `internal_id` silently fell back to the URL slug (`"2569"`, from `/property/2569/`), permanently losing the `"4-"` category prefix the agency's own site displays and that EstateWeb's original record was created with.

**Fix applied:** added `extractInternalIdFromSpecs()` to `crawler.utils.ts`, which reads the already-parsed `_detail_specs` table for a labeled code row (`Κωδικός`, `Κωδ.`, `Κωδικός Ακινήτου`, `Code`, `Reference`, `Property ID`) and returns it verbatim (prefix included). Wired in as the top-priority source — ahead of the free-text regex, after an explicit scraper-set raw field — in both `extractSourcePropertyIds()` (crawl-time) and the non-AI normalization fallback in `property-normalization.utils.ts`. Added unit tests in a new `crawler.utils.spec.ts`, including the exact `bitsimis-real-homes` regression case.

**Blast-radius audit (read-only, against all ~4,500 active source_properties platform-wide with a specs table):** only **73 properties** would get a different `internal_id` — **68 on `bitsimis-real-homes`** (all gaining back their missing numeric category prefix, e.g. `"2764"` → `"9-2764"`, `"900"` → `"4-900"`) and **5 on `housemarket-realestate`** (a missing `" S"` suffix, e.g. `"GE3618"` → `"GE3618 S"`). The other ~2,185 properties with a specs-table code already matched exactly (no change), and ~2,286 have no code-like label in their specs table at all (unaffected, still use the existing free-text/URL fallback). No other agency is touched.

**What this means going forward:** `internal_id` only refreshes when a listing is re-crawled, so this corrects itself agency-by-agency on each one's next scheduled crawl (for `bitsimis-real-homes`, that's Friday per the schedule above). Because `pushUpdate()` always resends the full payload including `code`, the corrected `internal_id` will get pushed to EstateWeb on the next sync too — for most of the 68 affected properties this will make our `code` match their true original EstateWeb code going forward. **Exception: property 2569 itself.** Its `UserProperty.integration_property_id` is still pointed at the *duplicate* (`59254`, not the original `51965`), so its next push will rename the duplicate's code to `"4-2569"` too — producing a second live listing with that exact code again, unless the duplicate is deleted/merged first (the "part a" cleanup from the prior update, still not done, still needs client confirmation).

## #4 — Found and fixed a serious flaw in the above before shipping it

Client instruction: triple-check this change for unwanted side effects, "especially not to create duplicates" — correctly, since re-review found the extraction fix above would, by itself, have **caused** new duplicates.

**What re-review found:** the extraction fix corrects `internal_id` for 73 properties platform-wide — but **64 of those 73 are already linked** to a live EstateWeb listing (`integration_property_id` set). The ownership check that gates every UPDATE (`listingBelongsToLinkedIntegration` / `listingBelongsToIntegration`) decided "does this still belong to us" by comparing the live listing's `code` against candidate codes built from `internal_id`/`property_id`. Once `internal_id` changes (exactly what the extraction fix does), the live listing's *already-pushed* code no longer matches the *new* candidates — the check would conclude "not ours," clear the link, and create a duplicate. Traced through step by step, confirmed this would have produced up to **64 new duplicates** on the agencies' next sync, i.e. a much bigger version of the original incident, caused by the fix meant to resolve it.

**Real fix:** the ownership check should never have depended on a code string match in the first place — our own computed code can legitimately change (exactly what just happened), while the CRM's record doesn't. Replaced it with the same identity check `reconcileCreate()` already uses to refuse a *coincidental* code match before CREATE (scope, address, price, sqm — compared only when both sides have a value): extracted into a shared `isEstateWebListingIdentityMismatch()` (`api/src/integrations/estateweb/utils/estateweb-listing-identity.util.ts`), used by:
- `EstateWebPropertyReconciliationService.isDefiniteCodeCollision()` (CREATE path, unchanged behavior, now de-duplicated).
- `CmsSyncOrchestratorService.listingBelongsToLinkedIntegration()` / `CmsSyncProcessor.listingBelongsToIntegration()` (UPDATE path) — now: id resolves (not 404) **and** no identity conflict ⇒ still ours, regardless of code. Removed the now-dead `buildEstateWebOwnershipCodes`/`estateWebCodeMatchesCandidates` code-matching helpers.

**A second, independent bug turned up while verifying this against live data:** the shared sqm comparison used a `< 0.01` tolerance, carried over unchanged from the original code. Checked all 64 already-linked affected properties against EstateWeb live (read-only `GET /api/property/:id` on each) and one failed purely on sqm — our `"53.29"` vs EstateWeb's live `53` (EstateWeb stores sqm as a whole number, rounding on push). That tolerance would have falsely flagged a real, correctly-linked listing as "different" and broken it too. Loosened to `<= 1`.

**Verified clean:** re-ran the live check against all 64 already-linked affected properties (both `bitsimis-real-homes` and `housemarket-realestate`) with the fixed tolerance — **64/64 pass, 0 mismatches**. Added regression tests (`estateweb-listing-identity.util.spec.ts`, including the sqm-rounding case; a new case in `cms-sync.processor.spec.ts` proving a fully-changed `internal_id` no longer breaks an existing link). Full `api` test suite: **19 suites / 217 tests pass**, `tsc --noEmit` clean.
