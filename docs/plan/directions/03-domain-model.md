# Domain Model — Property Sync

`api/prisma/schema.prisma` defines every model needed for the in-scope current phase. The outstanding migration action is running migrations when schema fields change (`api/prisma/migrations/`) and writing a seed script (`api/prisma/seed.ts`) for local development — both handled in Feature 01.

## Entity map (which feature owns which model)

| Feature | Models owned | Notes |
| --- | --- | --- |
| 01 — Foundation | `User` | Auth already implemented against this model; verify it works once migrated. |
| 02 — Agencies | `SourceAgency` | Root of the pipeline. `is_visible` / `is_enabled` gate end-user browse/track; `status` gates the crawl pipeline. |
| 03 — Scraper Management | `Scraper`, `ScraperVersion` | `Scraper` holds **no config** — always read `active_version.config`. |
| 04 — AI Generation | `ScraperGenerationRun`, `ComputerUseStep`, `Document` (screenshots) | `staged_config` lives only on the run until approved into a `ScraperVersion`. |
| 05 — Crawl Engine | `CrawlRun`, `ScraperExecutionTrace`, `JobLog` | Production execution. `CrawlRun.user_tracked_agency_id` attributes scheduled runs to a tracker. AI cost totals once Feature 06 finishes (or when a deferred batch completes). |
| 06 — Properties | `SourceProperty`, `Property`, `PropertySourceLink`, `PropertyHistory` | Normalization/dedup/history layer. Writes `CrawlRun` AI cost fields after normalization. |
| 07 — User Tracking | `UserTrackedAgency`, `UserProperty` | Per-user copy + preferences. `UserTrackedAgency.crawl_runs` links scheduled runs attributed to that tracker. |
| 08 — Notifications | `Notification` | Read by dashboard unread count. |
| 09 — Integrations Config | `IntegrationTarget`, `UserIntegration` | **`CmsSyncRun` is NOT used in this phase** — do not write to it. Exports AI credential resolver consumed by Features 04/06. |
| 10 — Dashboard & Users | (aggregation only, no new writes) | Reads across all of the above. |

## Key invariants to respect in every task

- **Single source of truth for scraper config**: `Scraper.active_version_id` → `ScraperVersion.config`. Never add a `config` field to `Scraper`. Every config change (AI or human) is a **new** `ScraperVersion` row; never mutate an existing version's `config`. Config JSON shape matches `scraper-generator` (`fields` with `{ selector, type }` defs, optional `detail_page`, pagination types: `next_button` | `load_more` | `infinite_scroll` | `url_param` | `none`) — see `scraper-generator/generate/prompt.js` and `scraper-generator/crawl/crawler.js`.
- **`ComputerUseStep` vs `ScraperExecutionTrace`**: the former logs the AI's exploratory generation-time loop; the latter logs a production Playwright run. Do not conflate them or write one from the other's code path.
- **`PropertyHistory` is append-only.** Every detected change (create, price, image add/remove, status change, removed, reappeared) writes a new row; never update or delete existing rows. `field` is `null` for `CREATED` / `REMOVED` / `REAPPEARED`.
- **`UserProperty` divergence rule**: when a crawl updates canonical `Property` data, the matching `UserProperty` is updated from canonical **unless** `is_modified` is `true` (user has local edits) — in that case, leave the copy untouched and do not silently overwrite; only a manual re-sync action may overwrite it. Always set `last_synced_at` when a copy is written from canonical. For crawls with `user_tracked_agency_id` set, automatic `UserProperty` create/update targets **that tracker user only** (not every enabled tracker for the agency).
- **`UserIntegration` AI credential rule**: every outbound AI API call (scraper computer-use generation, property normalization sync path, OpenAI Batch API upload/retrieve) must authenticate with an **active** `UserIntegration` row — never with platform env vars such as `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`. Map `AiProvider` → `IntegrationType` by enum name (`OPENAI` → `IntegrationType.OPENAI`, etc.). Read `api_key_secret` when the target's `auth_type` is `API_KEY` or `BEARER_TOKEN`. `UserIntegrationsService` (Feature 09) owns resolution and is exported for Features 04/06:
  - `resolveActiveApiKey(userId, integrationType)` — loads `UserIntegration` where `user_id`, `integration_target.integration_type`, `is_active: true`, and `api_key_secret` is non-null; throws `BadRequestException` with a clear message if missing.
  - `resolveForSourceAgency(sourceAgencyId, aiProvider)` — among **enabled** `UserTrackedAgency` rows for that agency with matching `ai_provider`, pick the earliest `created_at` row whose user has a resolvable key; return `{ userIntegrationId, apiKey, userId }`. Used for **self-heal** scraper generation (`ScraperGenerationRun`, `trigger: SELF_HEAL`). For property normalization when `CrawlRun.user_tracked_agency_id` **is** set, bill `resolveActiveApiKey(crawlRun.user_tracked_agency.user_id, integrationType)` for that tracker; when null, skip AI normalization.
  - Persist `user_integration_id` on `CrawlRun.metadata` (and on `ScraperGenerationRun.metadata` for self-heal) so async steps (batch webhook completion) reuse the same key.
  - **Manual generation** (`trigger: MANUAL`): use `resolveActiveApiKey(initiatedByUserId, ANTHROPIC)` where `initiatedByUserId` is the admin who called `POST /admin/generation-runs` (pass through the BullMQ job payload).
  - **Self-heal generation** (`trigger: SELF_HEAL`): use `resolveForSourceAgency(sourceAgencyId, ANTHROPIC)` — earliest enabled tracker on that agency with a resolvable Anthropic key.
  - **No key available**: fail the AI step (generation run → `FAILED`, normalization → skip AI with `CrawlRun` error/metadata + `// TODO(Feature 08)` notification); do not fall back to env keys. Raw crawl (`SourceProperty` upsert) may still succeed.
  - `OPENAI_WEBHOOK_SECRET` remains an env var — it verifies inbound webhooks only, not outbound API auth.
- **`CrawlRun.user_tracked_agency_id` attribution rule**: optional FK from `CrawlRun` → `UserTrackedAgency`. Set on **scheduler-enqueued** runs (one row per matching tracker). Null on admin **`run-now`** / **`rerun`** unless the prior run had the FK copied forward. `UserTrackedAgency.crawl_runs` is the reverse relation. The attributed tracker row drives AI prefs and billing for that run.
- **`UserTrackedAgency.crawl_interval` scheduling rule**: each tracker row stores a **cron expression string** (default `"0 */6 * * *"`). `SourceAgency` has no crawl schedule — scheduling is driven by enabled `UserTrackedAgency` rows. The cron scheduler (Feature 05) evaluates **each** enabled tracker independently: when its `crawl_interval` matches the current minute and its agency is `ACTIVE`, enqueue a `CrawlRun` with `user_tracked_agency_id` set to that tracker row. Overlap prevention is **per tracker** (no second enqueue while a run is `QUEUED` or `RUNNING` with the same `user_tracked_agency_id`). Multiple users tracking the same agency each get their own scheduled runs on their own intervals. Agencies with zero enabled trackers are not scheduled. Only `ADMIN`/`SUPER_ADMIN` may set or change `crawl_interval`; end users receive the default when they track an agency.
- **`UserTrackedAgency.use_ai_batching` routing rule**: AI property normalization (raw `SourceProperty` → canonical `Property`) can run either synchronously (Chat Completions) or via the OpenAI Batch API (50% cost discount, up to 24h turnaround). After a crawl upserts `SourceProperty` rows:
  - **When `CrawlRun.user_tracked_agency_id` is set** — read `use_ai_batching`, `ai_provider`, and `ai_model` from **that** `UserTrackedAgency` row only.
  - **When null** (admin manual run) — skip AI normalization unless product later adds an explicit admin billing path; raw `SourceProperty` only.
  - **Sync path** — `use_ai_batching: false`, or `ai_provider` is not `OPENAI`. Normalize immediately in the crawl pipeline (Feature 06) and proceed to `UserProperty` sync.
  - **Batch path** — `use_ai_batching: true` **and** `ai_provider: OPENAI`. Build a `.jsonl` batch input (`/v1/chat/completions`, one request per source listing with a stable `custom_id`), upload via Files API (`purpose: "batch"`), create the batch (`completion_window: "24h"`), persist the OpenAI batch id + pending source-property ids on `CrawlRun.metadata`, and return without blocking the crawl worker. When OpenAI sends `batch.completed` (verified webhook), download the output file, map results back via `custom_id`, finish normalization + history + `UserProperty` sync. Handle `batch.failed` / `batch.expired` / `batch.cancelled` by writing a `Notification` and storing the error on `CrawlRun.metadata` — never leave a crawl stuck silently.
  - Canonical data and user copies for batch-deferred listings must not appear until the batch completes; the crawl run itself may finish `SUCCESS` while `metadata.ai_batch_status` is `pending`.
- **`UserTrackedAgency.ai_provider` / `ai_model` selection rule**: each tracker row stores the user's preferred AI vendor (`AiProvider`: `OPENAI`, `ANTHROPIC`, `GEMINI`) and optional model id (`ai_model`, null = provider default for that integration). Feature 06 resolves normalization provider/model from the attributed tracker when `CrawlRun.user_tracked_agency_id` is set:
  - **FK set** — use that row's `ai_provider` / `ai_model`; resolve API key via `resolveActiveApiKey(tracker.user_id, …)`; persist on `CrawlRun.ai_model` + `CrawlRun.metadata.user_integration_id`.
  - **FK null** — skip AI normalization (raw crawl only).
  - **Batch path constraint** — applies only when the attributed tracker has `use_ai_batching: true` and `ai_provider: OPENAI` with a resolvable key. `ANTHROPIC` / `GEMINI` always use the sync path.
- **`CmsSyncRun` is out of scope.** It exists in the schema for the future sync phase only. No task in this plan creates, updates, or reads it.
- **`CrawlRun` AI normalization cost fields** (`ai_model`, `ai_input_tokens`, `ai_output_tokens`, `ai_input_cost`, `ai_output_cost`, `ai_total_cost`, `ai_average_cost_per_property`): populated by Feature 06 after normalization completes. All monetary fields are USD. `ai_average_cost_per_property = ai_total_cost / total_created` when `total_created > 0`, else `null`. On the batch path, leave these null until the OpenAI webhook worker finishes normalization. Mirror the shape of `scraper-generator/output/crawl/cost.json` (the local CLI also writes that file; production persists the same values on the `CrawlRun` row).
- **Duplicate grouping** is a flat `Property.duplicate_group_id` string shared by all members of a group; there is no separate `DuplicateGroup` table. Merge = assign the same `duplicate_group_id` to multiple properties; split = clear/reassign it on one member.

## Enums already defined (reuse, never redeclare)

`AuthRole`, `DocumentType`, `CrawlType`, `PaginationType`, `AgencyStatus`, `ScraperStatus`, `ScraperHealth`, `CrawlRunStatus`, `GenerationRunStatus`, `GenerationTrigger`, `ComputerActionType`, `JobStatus`, `PropertyStatus`, `ListingType`, `PropertyType`, `IntegrationType` (`ESTATEWEB`, `OPENAI`, `ANTHROPIC`, `GEMINI`, `DEEPSEEK`), `AuthType`, `CmsSyncAction` (unused this phase), `CmsSyncStatus` (unused this phase), `PropertyHistoryEventType`, `NotificationType`, `NotificationSeverity`, `AiProvider`.

**IntegrationTarget visibility rule**: `IntegrationTarget.is_visible` controls whether end users see a target on the Integrations page. Admins and super admins always see every target in admin CRUD regardless of `is_visible`. `UserIntegration.is_active` is separate — it enables/disables an individual user's connection.

**SourceAgency user-catalog rule**: `SourceAgency.is_visible` and `is_enabled` control the end-user agency browse/track experience only — they do **not** replace `status` (`ACTIVE` / `DISABLED` / `ARCHIVED`) for the crawl pipeline. Admins always see every agency in admin CRUD regardless of these flags.
- `is_visible` (default `false`) — when `true`, the agency appears in end-user `GET /agencies`. When `false`, hidden from users entirely.
- `is_enabled` (default `false`) — when `true`, end users may `POST /agencies/:id/track` (create/enable `UserTrackedAgency`). When `false`, a visible agency may still appear in browse but tracking is rejected (`400` with a clear message). Admins ignore `is_enabled` for scrapers, crawls, and tracker admin.
- End-user list filter: `status: ACTIVE` **and** `is_visible: true`. Include `is_enabled` on each row so the UI can disable the track control.

Per the API rule file, always import these from `generated/prisma` — never redeclare them as TypeScript unions in DTOs/interfaces.

## Migration & seed plan (Feature 01)

1. `npx prisma migrate dev --name init` against local Postgres to create the first migration from the existing schema.
2. `api/prisma/seed.ts` — seed at minimum: one `SUPER_ADMIN` user, one `ADMIN` user, one `USER`, so every subsequent feature has data to develop against without waiting on the crawl pipeline. Extend the seed incrementally as later features land (e.g. Feature 02 adds a couple of seed `SourceAgency` rows — at least one with `is_visible: true` and `is_enabled: true` for user browse/track dev; Feature 09 adds `IntegrationTarget` rows for `OPENAI`, `ANTHROPIC`, and `GEMINI` with `auth_type: API_KEY`, plus sample `UserIntegration` connections with dev keys for local testing).
3. Wire `prisma.schema`'s `generator client { output = "../src/generated/prisma" }` output — already generated once; regenerate after migration (`npx prisma generate`).
